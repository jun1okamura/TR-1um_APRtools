# コア幾何のパラメータ化（コア幅・TAP 列・オフセット・レーン）

作成: 2026-09-14 / 決定: **コア幅はトラックピッチ 5.4 µm の整数倍でパラメータ化する**

## 1. 単一パラメータと導出値

設計が書くのは **トラック本数 1 個だけ**にする。

```python
TRACK_PITCH       = 5.4                              # プロセス/ライブラリ固定
CORE_WIDTH_TRACKS = 299                              # ★設計固有はこれだけ
CORE_WIDTH_UM     = CORE_WIDTH_TRACKS * TRACK_PITCH  # = 1614.6
```

そこから機械的に出るもの（**現状ベタ書きされている値は全部これで置き換える**）:

| 導出値 | 式 | 現状 |
|---|---|---|
| `ROW_WIDTH_UM` | `CORE_WIDTH_UM`（横にマクロが無い場合） | 同じ値を 2 箇所に書いている |
| `CORE_OFFSET_X` | **`-(l + r) / 2`**（`l,r` = コアの native GDS bbox。§1-1） | SPI `-810.0` / I2C `-799.2` をベタ書き |
| コア bbox 幅 | **GDS 実測**（決め打ちしない。§1-1） | SPI 1632.6 / I2C 1611.0 をコメントで説明 |
| チップ座標の左右端 | `±(bbox 幅 / 2)` | SPI `±816.3` をベタ書き |
| `TAP_X_DEFAULT` | `tap_columns(CORE_WIDTH_UM)`（§2） | 4 要素のリテラル |
| `LANE_R0` | `snap_up(max(コア外縁, 他ブロック外縁) + LANE_CLEAR, LANE_PITCH)` | SPI `847.0` / I2C `815.4` / TD4 `810.0` をベタ書き |
| `VDD_BUS_Y` 等 | コア上辺 + クリアランスから導出 | ベタ書き（`route_chip.py` に 30 個以上） |

### 1-1. ★ オフセットは「行幅の半分」ではなく「実 bbox の中心」

`i2c_config.chip_geometry()` の実装が正:

```python
l, b, r, t = core_bbox_um(...)        # GDS 実測の native bbox
ox = round(-(l + r) / 2.0, 3)         # ← bbox を左右対称にする
```

既存 2 世代では結果的に `-CORE_WIDTH_UM/2` と一致するが、**これは偶然**:

| 設計 | 行幅 | native bbox 幅 | はみ出し | `CORE_OFFSET_X` |
|---|---:|---:|---|---:|
| SCLK_SPI | 1620.0 | **1632.6** | 左右とも +6.3 | −810.0 = −W/2 ✓ |
| APR_2026 | 1598.4 | **1611.0** | 左右とも +6.3 | −799.2 = −W/2 ✓ |
| **TD4** | 1598.4 | **1604.7** | **左だけ +6.3** | −W/2 では bbox が対称にならない |

TD4 の `chip_geometry()` のコメント: 「x が 1598.4 でなく 1604.7 なのは
**いちばん左のセルの N ウェル (140,0) が x=−6.3 まで出ている**ため」。

**はみ出しは行の両端に来るセル次第**（N-well は `WN.S1 = 4.0` / `AP.WN = 7.0` の帰結で
prBoundary から片側 6.3 µm 出るが、TAP や FILL が端に来ると出ない場合がある）。

→ **`CORE_WIDTH_UM + 12.6` と決め打ちしない。`core_bbox_um()` で GDS を測る。**
`CORE_WIDTH_UM` は行の幅、bbox は実測値、という区別を守る。

## 2. TAP 列の制約 — コア幅には上限がある ★重要

> **★ 534.6 は PDK の規則ではない**（U15、2026-09-16 に確認）。設計規則表に
> **TAP の最大間隔という規則は存在しない**（`Wmax` は M1/M2 の 45 だけ）。
> 「動いた実物と同じにしておく」という自前の慣習値で、超えたから不良という
> 性質のものではない。提出済みの SCLK_SPI（64.8 版）は最終間隔 **540.0** で
> 1 サイトぶん超えているが、**PDK の DRC デッキは通っている**。作り直した
> 59.4 版は 518.4 で慣習内。

TAP2（幅 10.8 µm）は `TAP_PITCH = 534.6 µm`（= 5.4 × 99、I2C 実チップ実測）以内の間隔で
並べる必要がある。配置は **x=0 から 534.6 刻み、最後の 1 本だけ行末（`W - 10.8`）に固定**。

```python
def tap_columns(W, pitch=534.6, tap_w=10.8):
    xs = []
    x = 0.0
    while x + tap_w <= W - tap_w:
        xs.append(x); x += pitch
    xs.append(W - tap_w)
    return xs
```

n 本の TAP 列で成立する条件は **最後の間隔が pitch 以下**:

```
(W - 10.8) - (n-2)*534.6  ≤  534.6
⇔  W  ≤  (n-1)*534.6 + 10.8
```

| TAP 列数 | 成立するコア幅の上限 | トラック換算 |
|---:|---:|---:|
| 4 | **1614.6 µm** | **299 トラック**（ちょうど 5.4 の整数倍） |
| 5 | 2149.2 µm | 398 トラック（開口 1840 に当たるので実質無制限） |

### ★ 既存設計の検算で見つかった不整合

実際の `placement.json` から TAP 位置を読み出した結果:

| 設計 | 行幅 | TAP x | 間隔 | 判定 |
|---|---:|---|---|---|
| APR_2026 | 1598.4 | 0 / 534.6 / 1069.2 / **1587.6** | 534.6, 534.6, **518.4** | OK |
| TD4 | 1598.4 | 同上 | 同上 | OK |
| **SCLK_SPI** | **1620.0** | 0 / 534.6 / 1069.2 / **1609.2** | 534.6, 534.6, **540.0** | **超過 +5.4 µm** |

**SCLK_SPI は最後の TAP 間隔が 540.0 µm** で、実測ピッチ 534.6 を 5.4 µm 超えたまま
提出されている。DRC は通る（TAP 密度は PDK の DRC ルールではない）が、基板/ウェル電位の
取り方としては設計意図から外れている。TD4 が「TAP ピッチを守るために 1620 を捨てて
1598.4 にした」のはこの問題を避けるため。

→ **再設計では 1620.0（300 トラック）を使わない。**

## 3. コア幅の選択肢

フレーム開口は四隅まで含めて **1840 × 1840 µm**（LEF の OBS ではなく GDS 実測値。
OBS は四隅を粗く塞いでいて「実在しない崖」を作るので使わないこと）。
コア bbox は最大で `W + 12.6` なので `W ≤ 1827.4`。

> **⚠ `i2c_config.chip_geometry()` の docstring 先頭に「開口は十字型」
> 「800 < |y| <= 920 -> |x| <= 800」という古い記述が残っている。**
> 同じ docstring の下の方で「壁は実ジオメトリで測る。LEF の OBS は … 実在しない崖」と
> 自己否定しており、読む人が必ず混乱する。APRtools へ移すときに消すこと。

（bbox 幅は「両端とも N-well がはみ出す場合」の値。実際は GDS で測ること。）

| トラック | コア幅 | bbox 幅(最大) | TAP 列 | 最終間隔 | 備考 |
|---:|---:|---:|---:|---:|---|
| 296 | 1598.4 | 1611.0 | 4 | 518.4 | **APR_2026 / TD4 実績**（LVS / DRC / ngspice 通過済み） |
| **299** | **1614.6** | 1627.2 | **4** | **534.6** | **4 列で取れる最大。ちょうど上限に一致** |
| 300 | 1620.0 | 1632.6 | 4 → **5 必要** | 540.0 → 違反 | SPI 実績（4 列のまま超過） |
| 338 | 1825.2 | 1837.8 | 5 | 210.6 | 開口の限界 |

**推奨は 296（実績踏襲）か 299（最大）**。299 にすると行あたり 16.2 µm（3 トラック）
広がるので、2 行なら論理セル 1 個分、配置率の余裕が少し増える。
1 トラック単位で振れるので、`explore_rows.py` / `sweep_seed.py` で
「行数 × コア幅」の掃引ができるようになるのが本来の狙い。

## 4. FILL の刻み（v59_4 で緩和されている）

64.8 版では **5.4 µm ちょうどの隙間が作れない**（FILL2=10.8 / FILL3=16.2 の組合せで
表現できないため、配置器がそうなる置き方を避けて次セグメントへ送っていた）。

v59_4 には **`FILL1`（5.4 µm）がある**ので、この制約は原理的には消える。
ただし TD4 の判断では既定オフ（`TD4_USE_FILL1=1` で有効）——
**「入れると隙間の刻みが変わって配置が丸ごと変わる」**ため、確定した結果を壊さない目的。

コア幅を 5.4 の整数倍でパラメータ化する以上、**`FILL1` を既定で有効にするのが筋**。
再設計時に有効・無効の両方で seed 掃引して比較すること。

## 5. `check()` に入れる検証項目

`apr/config_base.check()` が import のたびに見る（現状の `check()` に追加）:

```
□ CORE_WIDTH_UM % TRACK_PITCH == 0                     （整数倍）
□ CORE_WIDTH_UM + 2*NWELL_OVERHANG <= 開口幅(1840)      （フレームに収まる）
□ tap_columns() の最大間隔 <= TAP_PITCH                  ★SPI の 540.0 を弾く
□ TAP_X が全てサイトグリッド 5.4 に乗る
□ CORE_OFFSET_X == -(native_bbox.l + native_bbox.r)/2   （行幅の半分と混同しない）
□ native bbox 幅 - CORE_WIDTH_UM ∈ {0, 6.3, 12.6}       （はみ出しが想定外なら停止）
□ LANE_R0 >= コア外縁 + LANE_CLEAR                      （ベタ書き値の陳腐化防止）
□ len(CH_HEIGHTS) == N_ROWS + 1
□ ROW_WIDTH_UM <= CORE_WIDTH_UM
```
